# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Job Radar is one Next.js 16 app (App Router, JavaScript, Tailwind 4, SWR, Mongoose) holding both the UI and the API. It pulls remote developer jobs from public boards, scores them per user and tracks applications. See `README.md` for setup, deployment and the steps for adding a job source.

Next.js 16 differs from older versions: read the relevant guide in `node_modules/next/dist/docs/` before writing Next-specific code (`AGENTS.md`, regenerated by `next dev`). For example, middleware is `proxy.js`.

## Commands

```bash
npm run dev:memory    # app + throwaway in-memory MongoDB; safest way to try changes
npm run dev           # app using MONGODB_URI from .env, which may be a real Atlas database
npm run build
npm test              # everything: unit + API flows on in-memory MongoDB + local SMTP server
node --test test/password-reset.test.js                    # one file
node --test --test-name-pattern="a code stops" test/password-reset.test.js   # one test
npm run seed:admin -- you@example.com [password]
```

There is no linter or type checker configured. `dev:memory` reads `.env` too, so its `ADMIN_EMAILS` and `SOURCES_DEMO` apply if set. Only one `next dev` can run per project directory.

## Architecture

**API.** Route files in `app/api/**/route.js` stay thin and wrap their handler in `route()` from `lib/server/http.js`, which does the logging, rate limit (`limited`), JSON body parsing, DB connection, auth (`auth`, `role`) and error mapping. Handlers receive `ctx` (`req`, `params`, `query`, `body`, `user`, `status`, `headers`), return plain data to send as JSON, and throw `HttpError` for expected failures. Any other error is logged and becomes a generic 500. `parse(schema, data)` validates with zod.

**Server imports.** Route files import server code as `#server/...` (`imports` in `package.json`), never `@/`. Code in `lib/server/` and `app/api/` must also avoid `next/*` imports and use standard `Request`/`Response`. The reason is that tests import route files directly under plain Node, which can't resolve `@/` or `next/server`.

**GET routes must export `dynamic = 'force-dynamic'`.** Otherwise Next may try to prerender them at build time, and `route()`'s try/catch would swallow the dynamic bailout. New Mongoose models must use `mongoose.models.X || mongoose.model('X', schema)`, because Next evaluates modules once per route.

**Job flow.** All users share one `jobs` pool. `services/fetchJobs.js` upserts from each source in `services/sources/`, respecting per-source minimum intervals stored in `SourceFetch`. `services/matchUser.js` scores the pool against a profile (`score.js`) and writes `UserJob` rows: re-scoring never overwrites status or notes, and removes untouched `new` matches that no longer qualify. Fetch and match run on live search (throttled per user), profile save (match only), admin "Fetch now" and `GET /api/cron/daily`. `SOURCES_DEMO=1` reads `test/fixtures/` instead of the network, including in the deployed bundle (see `outputFileTracingIncludes`).

**Auth.** A JWT in the httpOnly `token` cookie. `requireAuth` reloads the user on every request, so role changes and disabling apply immediately, and rejects tokens whose `sv` doesn't match `user.sessionVersion`. Bumping `sessionVersion` logs out all of a user's sessions. `proxy.js` only checks that the cookie exists, as a redirect for pages; the API is the real gate.

**Forgot password** (`services/passwordReset.js`). Email → 6-digit code → one-time token → new password. Code and token are stored only as hashes. A correct code is used up and swapped for the token, so the password step can't fail on the guess limit. Responses mustn't reveal whether an account exists. Without `SMTP_HOST`, dev logs the code and production returns 503.

**Frontend.** Pages are client components fetching with SWR through `lib/api.js`; `useSession()` from `components/AppShell.js` gives the current user. SWR's cache outlives navigation, so a form filled once from `useSWR` must wait for `!isValidating` and update the cache after saving (see `app/(app)/profile/page.js`). Password fields use `components/PasswordInput.js`.

**Logging.** Use `logger` from `lib/server/logger.js`, not `console` (except CLI scripts). Pass errors as `{ err }`. Secrets are masked by field name only, so keep them out of message text. Don't add pino transports: their worker thread doesn't suit serverless hosts.

**Hosting.** The app must stay host-independent (Vercel now, possibly elsewhere later), so avoid platform-only APIs. `vercel.json` only holds the cron schedule. Docker uses `BUILD_STANDALONE=1`, which stays opt-in because standalone builds need symlink rights on Windows.

## Tests

`test/helpers.js` provides `client(ip)` and `dispatch()`, which call route handlers directly using a router built from `app/api`, with no HTTP server. So they don't exercise Next's bundling; check that with `npm run build`. Import `helpers.js` before anything that loads the logger, since it silences logs. Rate limits count per IP within a test process, so give each test its own `client('10.x.x.x')` if it makes many limited calls.
